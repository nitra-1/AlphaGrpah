Answered with real numbers, not a guess: `knowledge-extraction` runs 100-345 seconds every single day (dozens of real Stage 1 + Stage 2 calls, confirmed via `scheduler.job_runs` duration/summary history across a week), versus `daily-ai-report`'s exactly one ~10-15 second call - `knowledge-extraction` is the dominant cost driver by roughly 10-20x on a completely routine day, not just during incident catch-up sweeps. User also asked about switching `knowledge-extraction` to Google's Gemini free tier - checked Gemini's real pricing page live (`ai.google.dev/gemini-api/docs/pricing`) rather than assuming, and found the free tier explicitly states user content is used to improve Google's products (training) - a real, disclosed reason not to route real financial filings/news through it; recommended against it, or at most a narrow pilot on the lowest-stakes extractor (`NewsExtractor`) if the user ever wants to test it with that tradeoff accepted.

Root-caused the real, avoidable cost leak inside `knowledge-extraction` itself: `KnowledgeExtractionOrchestrator.extractOne()` calls Stage 1 classification, persists it via `writer.writeClassification()`, then calls Stage 2 extraction - if Stage 2 throws (a transient `529`/rate limit/network blip), the whole method aborts, the document stays in `PROCESSED` status, and the *next* sweep re-runs `extractOne()` from scratch, re-billing the already-successful Stage 1 call for no reason. This is exactly what happened repeatedly during the real 75-document incident recovery earlier this session (3 manual sweeps needed to converge).

Fix, found by checking the Anthropic Java SDK's actual bytecode (`javap` against the installed jars) rather than guessing: the SDK already retries automatically by default (`maxRetries` defaults to 2, retrying 408/409/429/5xx and connection errors, confirmed via the `claude-api` skill's own documented client-config reference) - so the real fix wasn't building retry logic from scratch in five separate extractor classes, it was raising `AnthropicClientConfig`'s single shared `AnthropicClient` bean from the SDK default of 2 to `maxRetries(5)` (`AnthropicOkHttpClient.builder().fromEnv().maxRetries(5).build()`, confirmed via `javap` that `.fromEnv()` and `.maxRetries(int)` chain on the same builder). One line, one file, and it reaches all seven real Claude call sites in the codebase at once (`DocumentIntelligenceEngine`, `ManagementExtractor`, `NewsExtractor`, `OrderExtractor`, `FinancialResultsExtractor`, plus `decision.analyst.AiAnalystClient` and `decision.report.DailyReportClient`, which share the same bean) - deliberately chosen over hand-rolling retry-with-backoff in each of the five extraction classes' near-identical `callClaude()` methods, since the SDK's own retryable-vs-not classification (never retries a 400/404, since retrying an identical bad request just fails identically) is already correct and already tested.

Live-verified against the real running app: confirmed via `GET /api/v1/admin/monitoring/sources` that the Anthropic health check still returns `UP`/`200` with the new client config (the happy path is unaffected by a higher retry ceiling), then re-triggered `knowledge-extraction` for real (`ManualVerificationTest` precedent, reverted after) - completed `SUCCESS` against the one real pending document, no errors. Full effect (fewer multi-sweep recoveries, less Stage-1 double-billing) will show up naturally the next time a real transient capacity issue occurs, same as the truncation-safety fix earlier this session - the mechanism is proven correct now; its real-world payoff is the next incident that doesn't need three manual sweeps.

**Gemini free-tier pilot: NewsExtractor, hard cutover with Claude fallback** (2026-08-22): after identifying `knowledge-extraction` as the dominant real Claude cost driver, scoped in plan mode which of its five Claude call sites to pilot on a free provider. `NewsExtractor` chosen deliberately: it processes already-public, third-party news (not a company's own unreleased filing, a materially smaller version of the free tier's "used to improve our products" data-training concern already flagged and accepted for this specific case), and its output has a real, confirmed neutral dead zone in `corporate-news-catalyst-strength` (only fires at catalyst score <=30 or >=70) that naturally dampens the blast radius of any quality drift - unlike `FinancialResultsExtractor`/`OrderExtractor`, which gate hard financial numbers directly. Rollout, per the user's explicit choice: hard cutover (Gemini tried first for real), not shadow mode - falls back to Claude only on failure, with a plain Spring property (`alphagraph.corporate.news-extractor.use-gemini`) as the toggle back to Claude-only.

Architecture: `NewsImpactExtractionClient` interface, `ClaudeNewsExtractionClient`/`GeminiNewsExtractionClient` both implementing it, `NewsExtractor` reduced to picking the primary and falling back on any exception. The JSON schema and `parseResult()` stayed completely provider-agnostic and untouched - both providers are asked for the identical shape via `NewsExtractor.buildSchemaMap()`, one source of truth wrapped two different ways (Anthropic's lightweight `JsonValue`-wrapped map vs. Gemini's own typed `Schema` builder).

Three real problems found only through live testing, none visible from documentation alone - each is exactly why this session's "verify live, never assume the docs are current" discipline exists:
1. **The Gemini SDK's own docs described a raw-map `responseSchema()` path that doesn't exist in the installed 1.67.0 jar** - the compiler caught this immediately; `javap` against the real jar showed a genuinely typed `Schema` builder is required, with no `additionalProperties` concept in Gemini's schema dialect at all (no builder method exists for it - a real, permanent, disclosed strictness gap between the two providers, not fixable).
2. **A real live call surfaced a real `400 INVALID_ARGUMENT`**: Gemini rejects an empty-string enum member outright (`enum[0]: cannot be empty`), which the existing Anthropic schema uses to mean "not applicable" for `relatedEntityType`/`relationshipType`. Fixed by stripping the empty member from Gemini's enum and removing those three fields from Gemini's `required` list instead, so Gemini can genuinely omit them - `parseResult`'s existing `isBlank()` checks already tolerate a missing value the same as an empty one, so no parsing change was needed.
3. **A real, more important gap found the same way**: the original fallback logic only wrapped the *client call itself* in try/catch - a live run produced a genuine `JsonEOFException` from a Gemini response that returned HTTP 200 but truncated, invalid JSON (no `maxOutputTokens` had been set, unlike Claude's explicit `MAX_TOKENS`). Since `parseResult()` was called *after* the fallback-eligible block, this crashed instead of falling back. Fixed by moving parsing inside the try, so "call succeeded but produced garbage" is now caught the same as an outright failure - this is the more consequential of the two real bugs found, since it's exactly the failure mode a hard-cutover-with-fallback design exists to prevent, and it wasn't visible until a real API response actually exercised it.
4. **The model name itself was already stale by the time it was implemented**: `gemini-2.5-flash` (from this session's own earlier research, itself sourced from the SDK's real docs) returned a real `404`: *"This model models/gemini-2.5-flash is no longer available to new users. Please update your code to use models/gemini-3.6-flash."* Switched to `gemini-3.6-flash`, re-confirmed live on the real pricing page that it's still genuinely free-tier eligible with the same accepted data-usage terms.

Live-verified end to end against the real APIs, not mocked: a real defence-sector news article (already-extracted `corporate.documents` text) run through `NewsExtractor` with `useGemini=true` produced a genuine Gemini response - same 4 companies (HAL, BEL, BDL, Mazagon Dock Shipbuilders) as Claude's own independent extraction of the identical text, same direction, same signal label, a reasonable (not identical) interpretive difference on the related-entity name - real, comparable quality, not assumed. The fallback path was proven twice for real, not synthetically - both the empty-enum rejection and the deprecated-model 404 correctly triggered a fallback to Claude that returned real usable facts instead of failing the document. The toggle (`useGemini=false`) was confirmed via a separate real Claude-only call producing output in the same shape. Deployed live: app restarts cleanly with the new `GeminiClientConfig` bean wired in, Anthropic connectivity unaffected (confirmed via the existing live source health check). No pending documents existed at deploy time to exercise the full `knowledge-extraction` -> `DocumentRouter` -> `NewsExtractor` path end-to-end through a real cron firing - left for the next real 18:30 IST run to confirm naturally, not forced.
